# Write-ups

On demand: read before writing a document for other people to read or act on — an analysis, a
proposal, a write-up to turn into tasks. Not for a chat reply, a README or a code comment.

- **A Markdown file**, never a page in a shared-docs service, unless asked.
- **Facts, not fault.** Say what each system does and what is missing. No word that judges or blames
  another team's work: "pretends", "fakes", "wrong", "honest error".
- **Only what moves the reader.** Every sentence helps understand the problem or choose a fix.
  Timings, internal names, side findings and caveats that change nothing stay out; a full analysis
  can be kept apart as a reference.
- **Written for people.** Say each outcome in words, linking the question it depends on: "the
  assistant says something first, if we decide so ([Questions #1](#questions)), or just drops".
  Never "as the first question decides", or a bare "need 2" or "option C".
- **Sources the team can open:** the tracker and the wiki. Never the repository's internal specs, and
  no tool words, like "triage" for an automated comment.
- **Few sections,** such as the problem, the ways to solve it, what to decide, what each team could
  add, with short examples. Drop one that would only repeat another.
