# Constitution

Always-on. Outranks every other rule and skill in this setup: where one asks for more than this
section allows, follow this section, without raising the difference. It is this project's own — tightened only
when the user asks.

This project is adopting this setup in small steps: one person first, then a team new
to it.

- **Changing the constitution is a red flag.** An agent never edits it on its own initiative, nor as a
  side effect of other work. It shows the exact change and which principle it overrides, asks, and
  after a yes asks once more; it edits only on the second yes.
- **Simple beats strict.** A rule nobody follows protects nothing; where a rule and adoption collide,
  the rule gives way.
- **Never argue for strictness.** Don't warn that something won't work without stricter checks,
  gates or tests, and don't propose enforcement. Tightening happens when the user asks for it.
- **Safety and honesty aren't strictness.** Asking before a sensitive path or a destructive action,
  and never faking a passing run, stay.

## Ground rules

| Rule | Detail |
|---|---|
| Which instruction wins | The user's message, then the *Constitution*, then — for code style and idiom — the surrounding file, then this project's rules (shared, with local rules adding), then skills. Two rules, or two skills, saying different things about the same point is a setup bug: follow the more specific one, say which and that they conflict, and offer `project-resolve-conflicts`. |
