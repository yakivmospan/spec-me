Encoding

Four ways a file gets into context

Every arrow in the three figures below is one of these, and the distinction is the whole point of the map: the cost of a file is not its length but its length multiplied by how often it loads.

Always — every session or every task, unconditionally
Conditional — a row in LOADER.md fires — or in .local/LOADER.md, which only the machine that has it reads — or a skill's description matches the request
Scripted — a skill runs a script, no judgement involved
Generated — written by build_index.py, never by hand

Figure 1 — the spine

One task, top to bottom

spec-builder-rules.md's Every task list is the only place the delegation flow is written down, and nothing else repeats it. This is that list, with what enters context at each step. Steps 3 – 8 are conditions, not a checklist: most tasks fire two or three of them.

Figure 2 — ownership

Every rule has exactly one home

The rule set applies its own Point, don't repeat to itself: the always-on file stays short by holding pointers, and the detail sits in files that only load when you are actually doing that thing. An arrow here means defers to — the source states the rule exists and the target owns what it says.

Figure 3 — the loop

The specs, and three files generated from them

Everything the agent reads for routing and history is derived, so it cannot drift from the specs the way a hand-maintained note would. The same pass runs five checks — and only one of them can fail the run.

The honest part

How rules are followed

Nothing enforces a rule. Every rule is followed by reading, the same way in both tools. When someone runs spec-rebuild-overviews, build_index.py reports the spec tree's structure — the one thing its --check fails on — and everything else as warnings.

Tightening is the user's call. No hook, CI job or gate is part of this setup; adding one is a decision a project makes when it wants to, not a gap to close.
